# ④ 타일 크기: 크게 만들수록 좋을까?

> **한 줄 답.** 큰 출력 타일은 입력 재사용을 늘리지만, 입력 조각과 중간 합을 보관할 공간이 커져 동시에 상주할 작업 수를 줄일 수 있다.

## 1. 출력 타일과 K 조각은 서로 다른 크기다

일반적인 타일은 출력 크기 `T_M×T_N`, K 조각 폭 `T_K`로 표현한다.

| 보관 대상 | 모양 | FP32 공간 |
|---|---|---:|
| A 입력 조각 | T_M×T_K | 4T_M T_K Byte |
| B 입력 조각 | T_K×T_N | 4T_K T_N Byte |
| 출력의 중간 합 acc | T_M×T_N | 4T_M T_N Byte |

출력 타일을 고정하고 K 방향으로 A·B 조각을 차례로 바꿔 누산한다. [Triton Matrix Multiplication의 Compute Kernel](https://triton-lang.org/main/getting-started/tutorials/03-matrix-multiplication.html#compute-kernel) 첫 블록 알고리즘에서 이 관계를 확인할 수 있다. 이번 연습만 `T_M = T_N = T_K = T`로 둔다.

입력 한 벌의 공간은 `8T² Byte`, 중간 합은 `4T² Byte`다. 한 변이 두 배면 각각 **네 배**의 저장 공간이 필요하다.

## 2. 단일 버퍼 기준의 공간 계산

아래는 **출력 타일 하나를 계산하는 작업 단위당** 필요한 논리적 데이터 크기다. `1 KiB = 1024 Byte`다.

| T | A 입력 버퍼 | B 입력 버퍼 | 입력 합계 | 중간 합 | 논리적 총합 |
|---|---:|---:|---:|---:|---:|
| 32 | 4,096 B (4 KiB) | 4,096 B (4 KiB) | 8 KiB | 4 KiB | 12 KiB |
| 64 | 16,384 B (16 KiB) | 16,384 B (16 KiB) | 32 KiB | 16 KiB | 48 KiB |
| 128 | 65,536 B (64 KiB) | 65,536 B (64 KiB) | 128 KiB | 64 KiB | 192 KiB |

전형적인 Shared Memory 타일링 설명에서는 A·B 입력 버퍼를 Shared Memory에 두고, acc를 스레드들에 분산된 레지스터에 둔다. **총합 192 KiB를 하나의 Shared Memory 요구량으로 해석하면 안 된다.** 두 자원은 각각 제한을 갖는다. 실제 배치는 구현·컴파일러·연산 경로에 따라 달라진다.

이 표에는 주소·루프 변수용 레지스터, 연산에 쓸 입력의 레지스터 복사본, 정렬·padding, 할당 단위에 따른 추가 공간이 없다. A·B를 두 벌 준비하는 이중 버퍼라면 입력 공간은 `16T² Byte`로 두 배가 된다. 중간 합 크기는 그대로다.

재사용 없는 방식은 출력 하나를 순차 누산하는 최소 논리 단위에서 A·B 스칼라 2개(8 B), acc 1개(4 B)가 필요하다. 전체 커널에서는 동시에 처리하는 출력 수만큼 이런 상태가 늘어난다. 스레드 배치를 지정하지 않았으므로 전체 레지스터 수로 단정할 수 없다.

## 3. 저장 공간이 동시 실행량을 제한하는 과정

한 SM에는 Shared Memory와 레지스터가 유한하다. 한 블록이 자원을 더 많이 차지하면 같은 SM에 함께 상주할 수 있는 블록 수가 줄 수 있다. Occupancy는 **상주하는 활성 warp 수 ÷ 하드웨어 최대 warp 수**다. 전체 커널의 블록 수나 연산 장치 사용률과 같은 뜻은 아니다. [CUDA Best Practices: Calculating Occupancy](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#calculating-occupancy)

```text
출력 타일 확대
  ├─ 입력 재사용 증가 → HBM 이동량 감소 → 메모리 시간 감소
  └─ 입력 버퍼·중간 합 증가 → 블록당 자원 사용 증가
                              → 상주 블록·warp 수가 줄 수 있음
                              → 다른 작업으로 지연을 숨길 기회 감소
```

자원 제한을 생각하는 간단한 식은 다음과 같다. 실제 계산에는 할당 단위와 스레드·warp·블록 수 제한도 적용된다.

$$
\text{상주 블록 수}\le
\min\left(
\left\lfloor\frac{\text{SM당 Shared Memory}}{\text{블록당 Shared Memory}}\right\rfloor,
\left\lfloor\frac{\text{SM당 레지스터 수}}{\text{블록당 레지스터 수}}\right\rfloor,
\text{기타 하드웨어 제한}
\right)
$$

이번 가상 하드웨어는 P와 BW만 주어졌다. SM별 자원 용량과 스레드 배치가 없으므로 **정확한 Occupancy나 128 타일의 실행 가능 여부는 계산할 수 없다.** 레지스터가 부족해 중간값이 메모리로 밀려나는 spill이 생기면 추가 이동이 발생하여 이번 계산 가정도 깨진다. 다만 Occupancy가 높다고 항상 더 빠른 것은 아니다. 재사용과 레지스터 보관으로 얻는 이점도 함께 평가해야 한다.

## 4. 출력 타일 크기 ≠ 스레드 수

출력 타일 크기는 계산할 **데이터의 개수**, 스레드 수는 그 작업에 참여하는 **실행 주체의 개수**다. 한 스레드가 여러 출력의 중간 합을 담당할 수 있다.

예를 들어 32×32 타일의 출력은 1,024개다. 이를 256개 스레드가 균등하게 나누면 스레드당 4개의 출력을 맡는 개념적 배치를 생각할 수 있다. 1,024개 출력이 곧 1,024개 스레드를 요구하는 것은 아니다. 같은 이유로 128×128 타일도 16,384개 스레드를 뜻하지 않는다.

Triton에서도 출력의 `BLOCK_SIZE_M`, `BLOCK_SIZE_N`과 실행 설정 `num_warps`는 별도 항목이다. 이번 주에는 특정 배치를 구현하지 않고 크기를 구분하는 데 집중한다.

## 5. K 폭만 늘려도 HBM 재사용이 늘까?

출력 타일을 고정하고 전체 K가 T_K로 나누어떨어지면, 한 출력 타일의 입력 이동량은 다음과 같다.

$$
\frac{K}{T_K}\times4(T_M T_K+T_K T_N)
=4K(T_M+T_N)
$$

이 단순 모델에서는 **T_K가 소거된다.** K 조각을 두 배로 하면 한 번에 읽는 양은 두 배지만 단계 수는 절반이 된다. 따라서 K 폭 확대만으로 총 HBM Byte가 줄지는 않는다. 버퍼 공간·동기화 횟수·파이프라이닝에는 영향을 줄 수 있다.

이번 정사각 타일 비교에서는 `T_M = T_N = T_K = T`로 두므로, 타일의 한 변 T를 키우면 K 조각 폭뿐 아니라 출력 타일의 행·열 수도 함께 커진다. 이에 따라 한 번 읽은 A 값은 타일의 `T_N`개 열 출력에, B 값은 `T_M`개 행 출력에 재사용되어 HBM 읽기가 줄고 산술 강도 I가 높아진다. 다만 이 가상 하드웨어의 Ridge Point는 `P/BW = 20 FLOPs/Byte`이며, `T=128`에서 `I ≈ 31.508 FLOPs/Byte`로 이미 연산 제한 구간에 들어선다. 이때 계산에는 최소 `F/P ≈ 6.872 ms`가 걸리지만, 메모리 이동 시간은 `Q/BW ≈ 4.362 ms`다. Roofline의 이상적 시간은 두 값 중 큰 값이므로, 타일을 더 키워 메모리 시간을 더 줄여도 연산 시간의 하한 아래로 내려갈 수는 없다. 이는 다른 하드웨어 자원 제약이나 실제 커널 실행 비용을 반영하지 않은 Roofline 모델의 결론이다.

**함께 이야기할 질문:** 출력 크기를 유지하며 T_K를 줄이면 입력 버퍼와 중간 합은 각각 어떻게 변할까? (입력 버퍼는 작아지고, 중간 합은 그대로다.)
