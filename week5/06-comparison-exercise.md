# ⑥ 같은 연산의 비교 조건표와 손계산

[5주차 목차](./README.md) · 이전 → [⑤ 측정](./05-measurement.md) · [제출용 양식](./comparison-template.md)

$$
Y=\operatorname{ReLU}(XW+b),\quad
X\in\mathbb{R}^{M\times1024},\quad
W\in\mathbb{R}^{1024\times1024},\quad
b\in\mathbb{R}^{1024},\quad M\in\{1,128\}
$$

b는 모든 행에 broadcast한다. 추론만 수행하며 학습·gradient·optimizer는 없다. 아래의 **설계 조건**, **문헌 확인**, **계산**, **아직 미측정**을 구분한다.

## 1. 먼저 비교 계약을 둘로 나눈다

| 조건 | A. 같은 연산 조건의 커널 비교 | B. 같은 품질 목표의 모델·시스템 비교 |
|---|---|---|
| 식·shape | 위 식, M=1과 128을 별도로 실행 | 동일 |
| 원본 데이터 | 모든 장치에 동일한 값·layout | 동일한 FP32 원본·동일한 평가 입력 |
| 입력·가중치 | X·W를 **한 번 BF16으로 반올림한 동일한 값** | FP32 원본에서 각 경로로 변환. 변환 방법 기록 |
| 계산·누산 | BF16 곱셈, FP32 누산 | 각 장치의 지원 경로 허용. dtype·양자화·누산 공개 |
| bias·ReLU·출력 | FP32. MatMul 뒤 저정밀도 저장을 끼우지 않음 | FP32로 출력 회수·비교. 내부 변환과 반올림 공개 |
| 희소성 | dense. pruning·2:4 sparse 경로 사용 안 함 | 기본 dense. 희소성 실험은 별도 행과 품질 검증 |
| 가중치 취급 | W·b는 장치에 상주하는 런타임 인수. 값의 상수 접기 제외 | 고정 모델 상수·prepacking 허용. 준비 비용 별도 기록 |
| 입력 취급 | X도 런타임 인수. 결과를 미리 계산해 상수로 대체하지 않음 | 요청마다 X 입력, 같은 평가 데이터 사용 |
| 측정 범위 | 전체 식의 장치 시간 또는 동기화된 호출 시간 중 하나로 통일 | 호스트 X → 호스트 Y의 전체 요청 시간, W·b는 정상 상태에서 상주 |
| 합격 조건 | 정밀도 계약 확인 + 공통 출력 오차 기준 통과 | 공통 품질 목표 통과 + 실행 경로·비용 공개 |

이 계약은 이번 수업의 제안이다. **NPU가 A의 BF16/FP32 계약을 지원한다고 문헌만으로 확인하지 못했으므로 세 장치의 A 결과를 억지로 한 표에 채우지 않는다.** NPU를 포함한 B 비교는 가능성을 조사하는 별도 실험이다. 각 장치의 실행 성공과 정확도는 아직 검증하지 않았다. [정밀도 근거와 한계](./03-specifications.md), [실행 지원 조건](./04-software.md)

같은 수학식과 같은 정밀도 계약을 유지하는 fusion·tiling은 A에서도 허용한다. 다만 fusion이 확인되지 않았다면 fused 커널이라고 부르지 않고 그래프 전체를 잰다. 온칩 누산 순서가 달라질 수 있으므로 bitwise 일치 대신 미리 정한 오차 기준을 사용한다.

## 2. 기준 출력과 허용오차를 맞추는 방법

다음은 재현 가능한 **평가 데이터 설계안**이며, 현재 문서에서 실제 입력 파일이나 장치 출력까지 생성한 것은 아니다.

1. 한 환경에서 고정 seed 목록 `0, 1, 2, 3, 4`로 FP32 데이터를 만든다. X는 `Uniform(-1, 1)`, W는 `Uniform(-1, 1)/sqrt(1024)`, b는 `Uniform(-0.1, 0.1)`로 정한다. 같은 이름의 seed만 각 프레임워크에 전달하지 말고 **생성한 배열 파일과 해시**를 공유한다.
2. M=1 입력은 해당 M=128 입력의 첫 행을 사용한다. W·b는 동일하다. 비교할 layout은 연속된 row-major로 정한다.
3. A에서는 X·W를 BF16으로 반올림한 값을 먼저 고정한다. 그 값을 CPU에서 FP64로 확장해 `ReLU(XW+b)`를 계산하고 마지막에 FP32로 반올림한 출력을 기준으로 쓴다. 입력 반올림 오차와 커널 실행 오차를 섞지 않기 위해서다.
4. B에서는 변환 전 FP32 원본을 FP64로 확장해 계산하고 FP32로 반올림한 값을 기준으로 쓴다. 이렇게 하면 양자화·저정밀도 변환의 오차도 평가에 포함된다.
5. 모든 원소가 아래 조건을 만족하는지 검사하고 최대 절대오차·실패 원소 수도 저장한다. NaN/Inf 출력은 실패다.

$$
|Y_i-Y_i^{\mathrm{ref}}|\le\mathrm{atol}+\mathrm{rtol}|Y_i^{\mathrm{ref}}|
$$

제안 기준은 A에서 `atol=1e-4, rtol=1e-4`, B에서 `atol=5e-3, rtol=1e-2`다. **이 값은 제조사가 보장한 오차나 세 장치가 이미 통과한 기준이 아니다.** 실험 전에 합의할 교육용 계약이다. 실패하면 실패로 기록하고 속도 순위에서 제외한다. 기준을 변경할 때는 모든 구현을 새 조건으로 다시 검증한다.

ReLU 근처의 0에는 상대오차만 사용하지 않는다. bias broadcast·음수 제거·배치 1 경계 처리를 확인할 입력도 추가한다. INT8 실험은 scale·zero-point·양자화 축·calibration 데이터와 평가 데이터를 구분한다. 실제 모델 비교로 확장하면 이 작은 식의 원소별 오차 대신 모델의 데이터셋·정확도 목표가 필요하다.

## 4. 연산량과 이동량 손계산

다음은 **A의 BF16 X·W, FP32 b·Y**를 사용하는 가상 메모리 모델이다. 실제 세 제품의 메모리 트래픽을 측정한 것이 아니다.

- 입력·가중치는 이미 장치의 큰 메모리에 있다. 호스트 전송은 세지 않는다.
- 한 호출 동안 X·W·b를 각각 한 번 읽고 Y를 한 번 쓴다. 호출 시작 시 온칩에 데이터가 없다고 가정한다.
- 누산·bias·ReLU의 중간 결과는 온칩에 유지한다. spill·padding·layout 변환·통신은 제외한다.
- 여기서 Q는 **큰 메모리 ↔ 칩 내부** 경계를 지나는 Byte다. 필요한 재사용을 모두 실현한다는 낙관적인 조건이며, 단순한 할당 용량 측정이 아니다.

MatMul은 FMA를 2 FLOPs로 세는 관례로 `F_mm = 2MKN`이다. bias는 별도로 `MN`번 덧셈, ReLU는 `MN`번 max/비교다. 아래 Roofline에는 **MatMul의 F_mm만** 사용한다. bias·ReLU까지 모두 행렬곱 peak로 처리한다고 가정하지 않는다.

$$
Q=2MK+2KN+4N+4MN
$$

| 항목 | M=1 | M=128 |
|---|---:|---:|
| MatMul, F_mm (FLOPs) | 2,097,152 | 268,435,456 |
| bias 덧셈 횟수 | 1,024 | 131,072 |
| ReLU max/비교 횟수 | 1,024 | 131,072 |
| X 읽기 (Byte) | 2,048 | 262,144 |
| W 읽기 (Byte) | 2,097,152 | 2,097,152 |
| b 읽기 (Byte) | 4,096 | 4,096 |
| Y 쓰기 (Byte) | 4,096 | 524,288 |
| 총 Q (Byte) | **2,107,392** | **2,887,680** |
| I = F_mm/Q (FLOPs/Byte) | **0.995141** | **92.958865** |

배치는 128배 커져도 가중치 읽기는 이 가정에서 같다. 전체 Q는 약 1.37배, 계산량은 128배가 되어 산술 강도가 크게 높아진다. 이것이 지난주의 데이터 재사용과 연결되는 부분이다.

중간 FP32 `XW`와 `XW+b`를 각각 큰 메모리에 쓴 뒤 다시 읽는다면, 두 중간 텐서 때문에 `16MN Byte`가 추가된다. 반대로 반복 호출의 W가 캐시에 남으면 큰 메모리에서 읽는 W 항이 줄어들 수 있다. **두 경우 모두 위 Q를 그대로 사용할 수 없다.**

## 5. 가상 장치: 연산 성능이 큰 장치가 항상 빠를까?

실제 제품명을 붙이지 않은 가상 장치 두 개를 정의한다. 둘 다 위 BF16 곱셈·FP32 누산 계약에 사용할 수 있는 peak라고 가정한다. 다른 연산과 제출 지연의 추가 비용은 생략한다.

| 가상 장치 | 연산 성능 P (TFLOP/s) | 큰 메모리 BW (TB/s, 십진수) | 경계 P/BW (FLOPs/Byte) |
|---|---:|---:|---:|
| A | 200 | 1 | 200 |
| B | 80 | 2 | 40 |

$$
t_{\mathrm{compute}}=\frac{F_{\mathrm{mm}}}{P},\quad
t_{\mathrm{memory}}=\frac{Q}{BW},\quad
t_{\mathrm{ideal}}=\max(t_{\mathrm{compute}},t_{\mathrm{memory}})
$$

| M | 가상 장치 | 연산 시간 (μs) | 메모리 시간 (μs) | 이상적 시간 (μs) | 모델에서 지배하는 자원 |
|---|---|---:|---:|---:|---|
| 1 | A | 0.010486 | 2.107392 | **2.107392** | 메모리 |
| 1 | B | 0.026214 | 1.053696 | **1.053696** | 메모리 |
| 128 | A | 1.342177 | 2.887680 | **2.887680** | 메모리 |
| 128 | B | 3.355443 | 1.443840 | **3.355443** | 연산 |

배치 1에서는 P가 작은 B가 대역폭 덕분에 모델상 두 배 빠르다. 배치 128에서는 가중치 재사용으로 B가 연산 성능의 한계에 걸리고, A의 이상적 시간이 더 짧다. **배치와 이동량 가정이 바뀌면 순위도 바뀐다.**

표는 주어진 모델의 시간 하한이다. 작은 행렬의 유닛 활용률·padding·제출 지연·bias·ReLU 비용·실제 캐시는 반영하지 않았다. 특히 다른 캐시 가정으로 측정한 시간이 이 표보다 짧다고 바로 오류라고 판정할 수 없다. 실제 H100·v5e·NPU의 속도를 이 가상 수치에서 추정하지 않는다.

[계산 스크립트](./calculate_comparison.py)를 실행하면 두 표를 재현한다. 공식은 [4주차 Roofline](../week4/02-roofline.md)의 `max(F/P, Q/BW)`를 이번 shape·dtype 가정에 적용해 직접 유도했다.

## 6. 지금 내릴 수 있는 결론과 보류할 결론

| 지금 설명할 수 있는 것 | 추가 확인 전에는 말할 수 없는 것 |
|---|---|
| 같은 식도 정밀도·fusion·메모리 경계가 다르면 조건이 달라짐 | 세 제품 중 이 연산이 실제로 가장 빠른 제품 |
| 배치에 따라 가중치 재사용과 산술 강도가 달라짐 | M=128이면 세 제품 모두 compute-bound라는 주장 |
| peak가 큰 장치가 항상 작은 지연시간을 주지는 않음 | NPU의 실제 FP32 누산 여부·두 shape의 컴파일 성공 |
| 단일 칩·여러 장치·시스템 전체의 수치를 구분해야 함 | 실제 J/sample, 서비스 처리량, 비용 대비 효율 |

이 보류 항목을 숨기지 않고 기록하는 것까지가 문헌 조사 과제의 완성이다.
